# Генератор черновика карточки товара (B2B, КИП)

Сервис принимает JSON с данными о приборе и возвращает черновик карточки для
контент-менеджера: SEO-заголовок, SEO-описание, характеристики, поисковые запросы
и commercial-блок. LLM: Google Gemma 4 31B через OpenRouter (бесплатный тариф).

Для запуска сервиса нужен только Docker. Для тестов нужен Python 3.10+.

## Запуск сервиса

1. Получите ключ на https://openrouter.ai/keys и создайте файл `.env`:
   ```bash
   cp .env.example .env      # впишите LLM_API_KEY
   ```
2. Соберите образ и запустите контейнер:
   ```bash
   docker build -t product-card .
   docker run -d --name product-card -p 8000:8000 --env-file .env product-card
   ```
3. Проверка: http://localhost:8000/health. Документация и форма для отправки
   запросов: http://localhost:8000/docs.

Полезные команды:
```bash
docker logs -f product-card                      # логи (ретраи, замечания проверки)
docker stop product-card && docker rm product-card
```
Если порт 8000 занят, смените порт: `-p 8080:8000`.

## Использование

```bash
curl -X POST "http://localhost:8000/generate?format=markdown" \
  -H "Content-Type: application/json" -d @examples/product_1.json
```

`POST /generate` принимает JSON товара. Параметр `?format=json` (по умолчанию)
или `?format=markdown`. `GET /health` проверка работоспособности.

Вход:
```json
{"name": "...", "manufacturer": "...", "specs": {"параметр": "значение"}, "description": "..."}
```
Обязательно только `name`. Пустые `manufacturer`, `specs`, `description` не ошибка:
они попадают в `missing_fields`, а в карточке стоит «данных нет».

Ответ: `card` (заголовок, описание, характеристики, запросы, commercial-блок),
`missing_fields` (чего не хватает во входе) и `warnings` (замечания проверки).

| Код | Когда |
|---|---|
| 200 | карточка готова (возможно, с `warnings`) |
| 422 | битый JSON, пустой `name`, `specs` не объект |
| 500 | ключ не задан или отклонён, внутренняя ошибка |
| 502 | модель дважды вернула непригодный ответ |
| 503 | LLM недоступна после ретраев (429/5xx/таймаут) |

Ошибки всегда в формате `{"error": {"code", "message", "details"}}`.

## Тесты

### Автотесты

Docker, сеть и API-ключ не нужны: LLM в тестах заменена заглушкой.

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pytest -v
```

Ожидаемый результат: все тесты `PASSED`. Покрыто: валидация входа (битый JSON,
пустое имя, неверный тип `specs`), проверка длин и чисел, retry при некорректном
ответе модели, коды ошибок и формат Markdown.

### Проверка на реальной модели

Нужен `.env` с ключом в корне проекта и то же виртуальное окружение. Запущенный
контейнер не требуется: скрипт вызывает код `app` напрямую.

```bash
python -m scripts.live_check                              # оба примера, по 3 прогона
python -m scripts.live_check --runs 5 examples/product_1.json
```

Для каждого прогона скрипт печатает длину заголовка и описания, число запросов
и `warnings`. Результат первого прогона каждого товара сохраняется в
`examples/outputs/` (JSON и Markdown). Модель недетерминирована, поэтому
прогонов несколько: так видно, как часто срабатывает retry.

Что проверять в результате вручную:
- в `card.specs` значения дословно из входа, без добавлений;
- в описании и запросах нет чисел, единиц, стандартов и сертификатов, которых нет во входе;
- для товара с неполными данными в `missing_fields` указаны пропуски, а в карточке «данных нет».

## Как исключаются выдуманные характеристики

1. **Блок характеристик собирает код**, а не модель: названия и значения
   дословно из входного JSON. Модель пишет только текст.
2. **Промпт** запрещает добавлять числа, единицы, стандарты и сертификаты,
   которых нет во входе, и задаёт правило «данных нет». Текстовые поля
   входа передаются как данные, а не как инструкции.
3. **Проверка после генерации:** числа из сгенерированного текста сверяются
   со входом (с учётом `1,6` и `1.60`). Длины проверяются кодом: заголовок ≤ 70,
   описание 800–1200 символов, 3–5 запросов.
4. **Один retry:** при нарушении модель получает свой ответ и точный список
   проблем. Если после retry остались замечания, они возвращаются в `warnings`,
   а не скрываются.
5. **Недостающие данные считает код** (`missing_fields`), а не модель.

## Структура

```
app/
  main.py        эндпоинты, обработка ошибок
  config.py      настройки из .env
  schemas.py     Pydantic-схемы входа и выхода
  llm_client.py  вызов OpenRouter, ретраи, разбор JSON
  prompts.py     системный промпт и retry-сообщения
  validators.py  missing_fields, длины, сверка чисел
  service.py     оркестрация: LLM -> проверки -> retry -> карточка
  render.py      JSON -> Markdown
tests/           pytest, LLM замокана
scripts/         live_check.py: прогон на реальной модели
examples/        входные данные и результаты (outputs/)
```

## Ограничения и что улучшить дальше

- Проверка чисел простая и может давать ложные срабатывания (например, «24/7»):
  такие случаи попадают в `warnings` для ручной проверки.
- Единицы измерения не проверяются.
- Бесплатный тариф OpenRouter имеет лимиты; при 429 клиент делает ретраи
  с задержкой, затем возвращает 503.
- Дальше можно: разделить API и LLM на два сервиса, добавить профили ожидаемых
  характеристик по типам приборов, пакетную обработку и кэш результатов.
